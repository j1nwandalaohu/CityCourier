# 街头骑手：功能完善版设计

日期：2026-10-18  
状态：四项功能范围已获用户授权；本书面设计待审阅，尚未开始实现。  
工作树：`D:/eleme/.worktrees/city-courier`，分支 `feat/city-courier`。  
基线：`c749674`。

## 1. 目标与边界

用户要求完善操作反馈、接单距离与路线预览、驿站／找车导航、订单历史。目标是让玩家知道为什么操作失败、接单前能判断路程、配送途中能找到驿站和停放车辆、结束后能查清收入与失败原因。

用户明确说明美术已在另一个 worktree 开发。本次主要修改功能 C++ 与测试，不修改美术工作树，不重做模型、材质、动画、地图或城市布局。保留现有单订单机制、配送时限与计费规则、车辆数值、恢复与救援规则。

本设计采用的默认值是：历史保留最近 20 单；驿站服务要求车辆距服务入口不超过 12 米；操作失败提示显示 3 秒。它们是本次设计选择，不是用户先前指定的数值。

## 2. 实现方案选择

推荐在现有订单、导航和资料子系统中增加明确的数据接口，UI 只负责展示与发起操作。这样失败原因、费用和历史都由实际执行规则提供，预览与正在执行的导航可以互不干扰。

两个替代方案：仅在 UI 中补提示实现较快，但会重复判定规则，无法可靠解决远距离充电和历史持久化；重建通用任务、导航与存档框架会扩大改动范围，当前四项功能不需要。采用前述增量扩展方案。

## 3. 操作反馈修复

### 玩家行为

- 按 E 后未成功，应显示最相关的具体原因。例如“请靠近至 2 米内”“目标被遮挡”“车速过快，请降至 3 km/h 或以下”“两侧空间不足，无法下车”。速度边界沿用现有不高于 3 km/h 的规则。
- 附近没有交互对象时显示“附近没有可交互目标”。失败提示不能使原本不可达的目标变成可交互对象。
- 驿站充电与升级失败时区分：尚未下车、玩家距离过远、车辆不在附近、车辆未停稳、正在充电、已满级、余额不足、资料不可用。
- 余额不足显示需要金额与当前余额。取消订单、救援、退出和重置的现有二次确认继续有效。
- 游戏内提示显示 3 秒，后续操作替换旧提示；菜单内保留本次操作结果，切换菜单时清除。自动检查不能持续刷失败提示。

### 规则与接口

交互、上下车及驿站服务提供统一的“成功／失败原因”结果；UI 和操作执行使用相同校验逻辑。尽量保留既有 bool 接口作为包装，降低与美术子类的集成冲突。

交互目标仍按既有可达性、优先级和距离选取。若无成功候选，按同样优先级在玩家 5 米内寻找失败提示候选；没有候选才提示“附近没有可交互目标”。只在玩家主动操作时反馈，不自动执行失败候选。

充电和升级都要求玩家在服务入口 2 米内、视线可达且已下车，车辆无人骑乘、速度小于 0.1 km/h、车辆位置与服务入口的三维距离不超过 12 米。12 米可容纳当前入口与道路之间的距离，无需移动美术场景。充电期间持续检查这些条件；条件失效立即停止，说明原因，不能凭空充满电。关闭服务界面仍取消充电。

涉及多个失败条件时，先返回对象／资料不可用，再返回玩家操作状态、玩家距离／遮挡、车辆状态／距离，最后返回充电状态、等级与余额，保证提示稳定。

## 4. 接单距离与路线预览

### 手机接单页

每张候选卡片展示：商家、收货点、基础配送费、承诺时限、预计取餐路程、送餐路程、总路程，以及“预览路线”和“接单”按钮。

距离使用现有道路图计算，包含连接道路和地点入口的路段，不使用两个地点的直线距离冒充道路距离。小于 1 km 显示取整米数，否则显示一位小数公里。

候选订单生成时保存位置与两段路程快照，显示“按刷新时位置估算”。时限沿用现有基于生成时总路程的规则；接单时不偷偷改变费用或承诺时限。空闲时提供“刷新订单”，重新生成 3 个候选和新的实例 ID；已有配送任务时不能刷新或再接一单。过期卡片的点击应明确失败，不接到另一张订单。

### 预览

点击预览后打开地图，分别标示“刷新时位置 → 商家”和“商家 → 收货点”，显示两段距离、总路程、商家和收货点名称；提供“返回接单页”。预览不自动接单，不修改当前导航目标。

候选距离与预览来自同一份路线快照。道路不可达的候选不进入可接单列表；运行时发现路线被阻挡时提示“路线暂不可用”，不能伪造穿墙的可通行路线。道路距离是路网估算，不承诺实时避让其他车辆。

## 5. 驿站／找车导航

### 导航模式

导航支持三种目标：订单目标、骑手驿站、停放车辆。手机提供“去驿站”“找车”“恢复订单导航”；没有活动订单时最后一项不可用并说明原因。地图绘制独立车辆标记。

接单默认切换至订单导航。取餐后，订单模式切换至收货点；玩家若主动选择了驿站或车辆，订单状态变化不会夺走其手动目标。结单清除订单模式目标，但保留有效的手动目标。重新开始游戏时不恢复临时导航。

找车仅在步行时可用；已骑车时提示“你已经在车上”。成功上车后结束找车模式，有活动订单则恢复订单导航，否则清除导航。到达驿站只显示到达提示，不自动充电或购买。

### 路线与反馈

HUD 分别展示当前配送任务与导航目标，避免把“前往驿站”误认为配送已取消。去驿站或找车时配送计时继续；提示玩家这一点。手机、地图、预览和历史页均沿用世界继续运行的规则；Esc 暂停仍冻结配送计时。

沿用道路图寻路，并补充到任意车辆位置的终点连接。路线终点读取实际车辆位置；不能把找车目标固定在出生点。道路连接段需通过可通行检查；无法连接时显示车辆位置标记和“无法规划路线，请返回道路”，不绘制穿越建筑的有效路线。

导航每 0.5 秒更新剩余路程与方向；目标改变、车辆移动超过 2 米或偏离路线超过现有 15 米阈值时重算。剩余路程以玩家在当前路线上的进度计算，不沿用生成路线时的静态总长度。有效路线上的终点距离不超过 2 米时提示到达；取餐、送达和上车仍需主动操作。

## 6. 订单历史与收入详情

手机增加“订单历史”入口，按结算顺序从新到旧展示最近 20 单，重启后保留。无记录时显示“还没有订单记录”；旧存档迁移后提示历史从本版本开始记录，不虚构过去订单。

每条记录包含订单 ID、商家与收货点名称快照、结算时间、完成／失败状态、实际用时、承诺时限、餐品完整度、基础费、实际收入、是否迟到和失败原因。失败原因区分超时、餐品损毁、主动取消、救援中止；失败订单收入为 0。结算时间存 UTC，界面显示本地时间；列表按写入顺序，避免系统时钟调整导致错序。

详情和结算页共用收入解释：先说明完整度影响，再说明迟到折扣，最终金额与现有整数分计费结果完全一致。若展示分项扣款，各项相加必须等于实际收入，不能因多次取整差一分钱。

订单终态只生成一次结算快照，资料子系统在同一次资料更新中写入余额、累计收入、完成／失败次数和历史。相同实例 ID 不得重复加钱或增加历史；保存失败后显示未保存并允许重试，重试只写现有快照。裁掉第 21 条旧记录不改变累计统计。

仍不保存进行中的订单；退出或重启不会凭空增加失败记录。历史不提供删除、搜索、排行或导出，本版不增加班次、多单配送和经营系统。

## 7. 存档升级与故障处理

资料版本从 1 升为 2。先识别并验证受支持的旧版本，再迁移至当前内存结构，最后执行当前版本校验；不能先用 Version == 2 的校验把版本 1 当作损坏。

迁移保留余额、累计收入、完成／失败次数、所有升级等级、音量和画质；新增历史为空。首次写入新版前保留有效旧主存档到现有备份位置，主文件继续采用原子替换与写后验证。备份恢复同样支持迁移版本 1。后续保存按现有滚动备份规则运行，不承诺旧可执行程序能够读取版本 2。

迁移保存失败时保留可读取的原文件和内存资料，提示保存失败并允许重试；不自动重置。未知更高版本不得被自动降级或覆盖，明确提示版本不兼容，沿用人工确认重置的保护流程。

历史上限 20 条，名称快照各最多 64 个 UTF-16 单元，截断时不拆分代理对；地点 ID 使用已验证的城市地点 ID。验证记录 ID 唯一性、枚举范围、数值有限性、费用／完整度范围及完成状态与失败原因的一致性。保留现有 64 KiB payload 上限，满容量与最长名称必须通过实际序列化大小测试。存档历史仅用于查询，不提供重放结算入口；当前会话结算去重集合保持不裁剪。

## 9. 验收

1. 在过远、遮挡、高速下车、两侧堵塞、余额不足和满级场景中，玩家得到对应原因；失败动作没有副作用。
2. 车辆停在站外超过 12 米时不能充电／升级；边界内且满足其他条件可服务；充电中离开条件失效时停止。
3. 三张订单卡的分段距离、总路程与预览一致；刷新旧 ID 失效；预览不接单或改变真实导航；接单费用与时限保持一致。
4. 有单时可以去驿站、找车并恢复订单导航；计时继续；上车正确退出找车；无路、偏航和车辆移动有正确反馈。
5. 完成、迟到、超时、损毁、取消及救援各有准确历史与收入；重复回调、重复保存和重载不会重复结算。
6. 第 21 条记录只淘汰最旧历史；新旧存档、旧备份、写入失败、损坏和未知版本分别有验证，旧资料字段完整保留。
7. 历史页空态、满容量滚动、中文文本与新增按钮可用；Tab、M、Esc、鼠标和返回行为不会卡住输入或重复触发操作。
8. 原有自动化回归通过；新增规则测试覆盖边界而非重复实现；Editor 编译、Development 与 Shipping 打包通过，并在隔离 UserDir 中验证实际游戏界面和完整配送流程。不得用用户真实进度进行破坏性测试。

发布时更新操作说明与验证结果，明确区分自动化测试、实际打包验证和未验证项目。本设计文件不代表代码或游戏包已经完成更新。
