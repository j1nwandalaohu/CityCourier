# 中国城市外卖员游戏：首版设计

日期：2026-10-17

项目代号：CityCourier；中文暂用名：街头骑手

状态：设计与实施计划已获用户确认，2026-10-17开始按当前会话顺序实施；任务1进行中。

## 1. 目标与已确认范围

用户已确认：Windows 电脑端、UE5、中国城市小街区、完整配送流程。用户希望游戏具有 GTA 式的城市观感和自由行动体验，玩家的核心身份是外卖员。

首版交付目标是一个能独立启动的 Windows 单人 3D 游戏：玩家能在街区步行、上下电动车、接单、取餐、骑行送餐、结算收入并购买车辆升级。首版完成标准包括可玩的配送循环和经过打磨的代表性街段；只有文字、工程骨架或方块场景均不代表首版交付完成。

以下细节是为执行而提出的默认设计，用户可在本文审阅时调整：虚构中国南方城市、固定傍晚、键鼠操作、同时只配送一单、约 600 × 600 米地图、4 家商户、8 个收餐点、轻度拟真驾驶。首版不承诺达到 GTA 的资产规模或最终画面精度。

核心体验：在有烟火气的街道里，通过熟悉路线和掌握驾驶技巧提高配送效率，用收入改善车辆。

## 2. 城市与视觉

### 2.1 地图结构

地图可游玩区域约 600 × 600 米，包含一条可环行的主路、贯通各区域的支路和至少两条可骑行近路。以道路连通性和可辨认的地标组织地图，避免孤立配送点。

| 区域 | 视觉识别 | 玩法用途 |
| --- | --- | --- |
| 商业街 | 连排店面、中文灯箱、便利店、路边停车 | 两家取餐商户，主要驾驶路段 |
| 老小区 | 围墙、门岗、楼栋编号、晾衣设施 | 三个收餐点，步行交付 |
| 城中村 | 窄巷、空调外机、杂货店、密集招牌 | 一家商户、三个收餐点、两条近路 |
| 夜市 | 餐车、遮阳棚、暖色灯泡、食客 | 一家商户、两个收餐点 |

玩家起点是一处骑手休息站，提供车辆停放、充电和升级交互。地图外缘以连续建筑、围墙和路障形成边界，出口有清晰提示。每个商户和收餐点都需要有可达的步行交互区。

### 2.2 美术方向

采用真实尺度、写实材质、第三人称镜头和偏暖的傍晚光照。重点资产为外卖员、带餐箱的电动车、商铺门面、居民楼入口、道路与街道杂物。提供角色基础站立、行走、跑步和骑行姿态；上下车在首版使用短暂过渡及安全定位。

店铺使用原创中文名称和图形；人物、地图和品牌均独立设计。美术素材需要记录来源和使用许可，不能把未知来源素材作为可发行资产。开发过程可使用清晰标记的占位素材，但交付时应替换影响主要体验的角色、车辆和代表性街段占位物。

首版至少打磨一段约 150 米长的商业街，含连续门面、地面细节、招牌、街灯、角色和电动车；其余区域使用视觉一致的模块化建筑。固定时间与晴朗天气，避免同时制作昼夜和天气系统。

### 2.3 人车与声音

同屏上限初设为 6 辆背景车和 12 名行人，远处停用或隐藏。车流沿固定车道巡行，遇到玩家或前车减速停车；行人沿人行道巡行并在障碍前停下或调整方向。首版不模拟完整城市交通系统。

车辆碰撞和建筑碰撞生效，背景角色不包含受伤或死亡系统。提供电动车行驶、刹车、城市环境声、接单提醒和交付音效，音量可调。

## 3. 玩家控制与驾驶

### 3.1 默认输入

| 输入 | 步行状态 | 骑行状态 / 其他 |
| --- | --- | --- |
| W / A / S / D | 前后左右移动 | 加速 / 左转 / 制动及低速倒车 / 右转 |
| 鼠标移动 | 转动镜头 | 转动镜头，停止输入后缓慢回正 |
| Shift | 跑步 | 不额外加速 |
| Space | 无动作 | 强制动 |
| E | 上车、取餐、交付、休息站交互 | 在安全位置下车 |
| Tab | 打开或关闭订单手机 | 同左 |
| M | 地图 | 同左 |
| R（长按 2 秒） | 回到最近安全位置 | 连人带车恢复到最近安全道路点 |
| Esc | 暂停与设置 | 同左 |

交互提示只显示当前距离内优先级最高的一项。取餐、交付与休息站操作要求步行且距离目标不超过 2 米。骑行速度不高于 3 km/h 才能下车；左右都没有安全落脚空间时拒绝下车并显示原因。

打开手机或地图时世界继续运行，松开油门并自动制动；订单计时继续。Esc 暂停整个单人世界和订单计时。输入模式切换后不得残留油门或转向输入。

### 3.2 电动车手感

采用有碰撞扫掠的街机式电动车控制器，提供加速度、制动、速度相关转向、坡面贴合和视觉侧倾。车体保持稳定，首版没有真实两轮自平衡模拟。车辆状态与角色步行状态使用明确切换；骑行时只保留必要的碰撞体，避免车与骑手相互推挤。

初始前进最高速度 36 km/h，倒车最高速度 6 km/h。低速转向灵活，高速转向受限。相机通过碰撞检测避免穿墙，狭巷中缩短跟随距离。车辆不可穿过建筑或通过尺寸不匹配的缝隙。

R 恢复使用最近记录的安全道路位置，并以碰撞检测确认落点；没有安全记录时回休息站。保持订单状态和餐品完整度，当前订单计时额外消耗 5 秒，并立即评估是否进入超时或失败状态；恢复不会充电或修复餐品。

### 3.3 电量与升级

满电基础续航按实际移动距离计算为 3 公里；倒车也消耗电量，安全恢复的瞬间位移不计入里程。电量低于 20% 提示，归零后停止驱动车辆，仍可下车步行。休息站免费充满电，交互耗时 5 秒，取消则不充电。电量归零且车辆离休息站超过 20 米时，手机提供“呼叫救援”：连人带车回休息站并充满电，不扣除余额；仅存在活动订单时取消该单并记录一次失败。

三种升级各有两级：

| 升级 | 第一级 | 第二级 | 两级价格 |
| --- | --- | --- | --- |
| 动力 | 最高速度 42 km/h | 最高速度 48 km/h | ¥60 / ¥120 |
| 操控 | 转向响应提升 10% | 累计提升 20% | ¥40 / ¥80 |
| 电池 | 续航 4 公里 | 续航 5 公里 | ¥50 / ¥100 |

升级在休息站购买，依次解锁；不允许负余额、跳级、重复扣款。购买电池升级保持原有电量百分比，充电独立处理。初始余额为 ¥0。

## 4. 接单、配送与结算

### 4.1 手机与导航

手机订单列表显示 3 个候选订单，每项列出商户、目的地、基础收入和时限。接单后锁定为一个活动订单，其他订单不可同时接取；终结活动订单后生成新的候选列表。候选订单从有效商户与收餐点组合中生成，不要求联网。

HUD 显示当前目标、剩余时间、餐品完整度、余额、速度和电量。小地图显示玩家、当前取餐或送达点及道路导航线；全屏地图支持查看整个街区。路径按可骑行道路图计算，取餐/交付入口之间的步行部分使用清晰标记。偏离路线后重新计算；路线不可达时显示目标方向与原因，不能绘制穿越建筑的假导航。

### 4.2 状态与时间规则

正常状态流：候选 → 已接单待取餐 → 已取餐配送中 → 已完成。

失败分支：待取餐或配送中可因最终超时、主动取消、救援而失败；配送中还可因餐品完整度归零失败。成功或失败均是终态，每个订单实例只终结一次。

计时从接单开始，取餐与送达都包含在时限内。设 L 为玩家当前位置到商户、再到收餐点的规划道路总长度（米），订单时限为 clamp(ceil(90 + L / 5), 120, 300) 秒。时限在候选订单刷新时计算并显示，接单时固定，之后不会因为重新规划路线而增加。

显示时限用尽后进入 60 秒宽限期：已取餐的玩家仍可交付，但按超时订单降价结算；尚未取餐的玩家也可继续取餐。到达“时限 + 60 秒”或更晚即失败，不再允许取餐或交付。交付时间等于正常时限时计为超时，等于最终失败时刻时失败。

取餐要求当前订单处于待取餐状态，并在对应商户交互范围内。送达要求已取餐、目标匹配、玩家步行且在收餐点范围内。错误目标、过远交互和重复按键均不得改变订单或余额。

### 4.3 餐品完整度与收益

取餐时完整度为 100%。仅已取餐且玩家正在骑乘时的有效车辆撞击造成损失；基于碰撞表面的法向接近速度计算，避免擦墙持续扣除。低于 8 km/h 不扣损，达到阈值后每次扣除 clamp(round((v - 8) × 1.5), 1, 30) 个百分点，其中 v 的单位为 km/h；伤害事件至少间隔 1 秒。完整度最低为 0%，归零即失败。

订单基础收入按商户和收餐点组合配置为 ¥16–¥32，金额全部用整数分保存。实际收入为：

`floor(基础收入分 × 完整度百分比 / 100 × 时间系数)`

时间系数：准时为 1，宽限期内为 0.6；整数运算以 100 或 60 的百分比表达，最后一次向下取整到分。结算界面显示基础收入、损餐影响、超时影响和实际收入。失败或主动取消收入为 0，不扣已有余额。

统计完成单数、失败单数和累计实际收入。完成单数包括宽限期内成功交付的订单。接单、取餐、结算、购买升级都必须防止重复输入产生重复状态变化。

## 5. 软件结构与数据职责

基线采用 UE 5.6，Windows x64，C++ 管理玩法规则与状态，Blueprint 管理可视化资产配置与交互呈现，UMG 制作中文界面，Enhanced Input 管理键鼠输入。5.6 是本项目选择的版本基线，不表示它是最新版本。

| 单元 | 唯一主要职责 | 与其他部分的关系 |
| --- | --- | --- |
| 游戏流程 / PlayerController | 开始、暂停、输入模式、角色控制切换 | 读取玩法状态，向角色和界面路由输入 |
| CourierCharacter | 步行、相机、交互检测、上下车 | 不直接计算订单收益 |
| ScooterPawn / 移动组件 | 骑行、碰撞、电量、安全恢复 | 广播有效撞击事件，读取已购升级 |
| DeliverySubsystem | 候选订单、状态机、计时、结算资格 | 验证交互目标，发出一次性结算事件 |
| 商户 / 收餐点 Actor | 稳定地点 ID、名称、交互位置 | 提供地点身份，不直接修改余额 |
| RoadGraph / 导航服务 | 连通道路、最短路径、地图线条数据 | 为订单时限、导航与车辆恢复提供位置数据 |
| ProfileSubsystem / SaveGame | 余额、统计、升级、保存与读取 | 接收合法结算、执行升级交易 |
| HUD / 手机 / 结算界面 | 显示状态、收集用户操作 | 通过受验证接口发起操作，不拥有权威订单数据 |
| 背景交通与行人 | 有限范围内的巡行和避障 | 不生成订单，不改变存档 |

静态配置使用 DataAsset / DataTable：地图地点、订单基础收益、车辆参数、升级价格和道路图。每个地点使用唯一 ID，显示名称可单独修改。开发内容放在独立的 CityCourier 目录中，避免修改引擎文件。

运行时订单包含唯一实例 ID、商户 ID、收餐点 ID、基础金额分、固定时限、已用时间、完整度和状态。结算由订单系统验证终态并以实例 ID 防重后提交到玩家资料；界面重复事件不得再次加钱。

在建图或载入时检查地点 ID 重复、商户/收餐点缺失、道路不连通及出生点无效；有错误的订单组合不能进入候选列表。地图关键配置缺失时显示具体开发错误，而不是开始一个无法完成的订单。

### 5.1 存档

保存余额、累计收入、完成/失败单数、升级等级、音量、画质设置和存档版本号。成功结算、订单失败、购买升级和修改设置后保存；退出时再次保存。

首版不恢复进行中的订单、位置或电量。重新启动后玩家与满电车辆出现在休息站，活动订单被丢弃，不计收入或失败。这个规则需要在退出确认中明示。已结算收入与已购升级必须保持。

首次启动创建默认资料。存档损坏时提示并尝试上一个有效备份；无可用备份时允许以新资料开始，保留损坏文件用于排查。保存失败时提示“本次进度未保存”，保留内存中的有效进度并允许重试，不能报告保存成功。

初始存档版本为 1；读取时校验版本、金额非负、升级等级在 0–2 范围内。未知版本视为不兼容，提示后允许建立新资料，先保留原文件；首版没有历史格式迁移需求。每次保存先写临时快照并确认成功，再更新主存档并保留上一个有效版本。

## 6. 性能、环境与交付

### 6.1 已观察到的本机环境

2026-10-17 通过只读本地检查得到：

- GPU：NVIDIA GeForce RTX 3060 Ti，nvidia-smi 报告 8192 MiB 显存。
- 系统内存：约 15.8 GiB。
- Visual Studio 2022 Build Tools：17.14.29；已检测到 x86/x64 C++ 工具组件，尚未通过 UE 实际编译验证。
- 空闲磁盘：C 盘约 70.2 GiB，D 盘约 56.4 GiB，数值会随使用变化。
- 在 PATH、常见 Epic 注册表项、常见安装目录和 Launcher 安装清单路径中未发现 UE5；此检查不能排除其他自定义安装位置。
- 当前项目目录最初为空，未包含现有 Unreal 工程或 Git 仓库。

实施时需要先建立可工作的 UE 5.6 引擎与匹配编译环境，核对实际 MSVC、Windows SDK 和 .NET 组件，然后完成一个空项目的编译、启动和 Windows 打包验证，才能声称开发环境可用。UE 安装位置及磁盘使用须基于实际安装选项检查；现有磁盘数字不等同于已确认足够。需要用户账户登录的步骤由用户完成，不读取凭据。

### 6.2 渲染与性能目标

默认提供低、中、高三档，1080p 中档以 30 FPS 为首版最低验收目标，60 FPS 为优化目标，均以打包后的实测为准。中档采用软件光线追踪路径的 Lumen 配置，不启用硬件光线追踪；低档使用更轻的光照与阴影配置。只有适用的静态场景资产使用 Nanite，不能假设打开特性就自动获得性能收益。

优先复用模块化网格、实例化重复物件、控制材质数量、纹理分辨率、阴影距离与背景实体数量。首版采用单个小型关卡，不引入大型开放世界分区系统。计时和移动逻辑不依赖固定帧率。

性能验收使用同一条 3 分钟配送路线，记录分辨率、画质档、打包配置、平均帧率、1% low 和峰值资源占用。中档平均不低于 30 FPS、1% low 不低于 24 FPS 是目标；未达到时如实记录并继续优化，不能以编辑器空场景的帧率代替。

- 功能验证与性能实测记录，明确已知问题。
